# DroidBlend 候选配置筛选报告

## 1. 数据来源与筛选标准

数据来源：`results/hybrid_by_ratio/ratio_0p10` 到 `ratio_0p50` 下的 `summary.json`。

`receiver_full` 作为 receiver 完整 prefill 的质量参考基线，在五个 token ratio 批次中都会被重复记录。实测结果如下：

|结果目录|F1|mean latency|p50 latency|p95 latency|样本数|
|---|---:|---:|---:|---:|---:|
|ratio_0p10|0.8004|0.0513s|0.0408s|0.0871s|50|
|ratio_0p20|0.8004|0.0513s|0.0401s|0.0845s|50|
|ratio_0p30|0.8004|0.0496s|0.0395s|0.0862s|50|
|ratio_0p40|0.8004|0.0515s|0.0414s|0.0847s|50|
|ratio_0p50|0.8004|0.0532s|0.0404s|0.0867s|50|

跨五批次汇总：`receiver_full` 的 F1 为 0.8004；mean latency 平均为 0.0514s，范围为 0.0496s 到 0.0532s；p50 latency 平均为 0.0404s，范围为 0.0395s 到 0.0414s；p95 latency 平均为 0.0858s，范围为 0.0845s 到 0.0871s。


本次只筛选真正的融合实验：`hybrid_layers_*_ratio_*`。固定基线为同一连续重算层段的 `droidspeak_layers_*`。

筛选标准：

```text
DroidBlend F1 >= 同层段 DroidSpeak F1
```

这对应当前实验目标：DroidBlend 作为 DroidSpeak + CacheBlend 的融合方案，首先必须保证 F1 不低于 DroidSpeak 基线；在满足该条件后，再比较 receiver-side prefill + first-token preparation latency。

## 2. 总体筛选结果

## 5. 按额外时延排序的候选

从“相对同层段 DroidSpeak 多花多少时间”看，额外时延最小的候选大多出现在重算层数较多的区间：

|token ratio|完整重算层段|完整重算层数|F1|F1 提升|p50 latency|额外 p50 latency|估计重算工作量|
|---:|---:|---:|---:|---:|---:|---:|---:|
|0.10|2-31|30|0.8270|+0.0000|0.0558|+0.0007|97.19%|
|0.20|2-31|30|0.8270|+0.0000|0.0559|+0.0010|97.50%|
|0.10|0-31|32|0.8004|+0.0000|0.0561|+0.0013|100.00%|
|0.40|4-31|28|0.8270|+0.0067|0.0552|+0.0018|94.38%|
|0.10|4-31|28|0.8270|+0.0067|0.0553|+0.0020|91.56%|
|0.10|6-31|26|0.8204|+0.0200|0.0548|+0.0033|85.94%|
|0.10|2-25|24|0.8004|+0.0000|0.0531|+0.0042|80.31%|

这说明一个现象：完整重算层数越多，DroidBlend 相对 DroidSpeak 的额外开销越小，因为可做 sparse token 重算的剩余层更少。但这类配置的重算工作量很高，不一定符合“减少重算”的最终目标。

## 6. 推荐进入下一阶段的配置

建议下一阶段不要只保留一个点，而是保留三个方向：

|用途|token ratio|完整重算层段|原因|
|---|---:|---:|---|
|低时延优先|0.10|8-21|所有通过筛选配置里 p50 latency 最低，F1 比同层段 DroidSpeak 高 0.0076|
|低重算层数探索|0.30|12-19|只完整重算 8 层，F1 比 DroidSpeak 高 0.0495，p50 仍接近最快区间|
|高质量保持|0.10|2-25|F1 达到 0.8004，额外 p50 latency 只有 +0.0042s|
|质量提升优先|0.40|6-25|F1 达到 0.8137，比 DroidSpeak 高 0.0200|
|高质量低额外开销|0.10|6-31|F1 达到 0.8204，额外 p50 latency +0.0033s，但重算工作量较高|

如果只能先跑少量复验，我建议优先顺序是：

```text
1. ratio=0.10, span=8-21
2. ratio=0.30, span=12-19
3. ratio=0.10, span=2-25
4. ratio=0.40, span=6-25
5. ratio=0.10, span=6-31
```

## 7. 后续是否还能更好

有机会继续提升，但现在需要更细的实验设计：

1. 当前还没有出现 latency 低于 DroidSpeak 的配置，说明 sparse token 重算带来的额外操作、cache 拼接、layer-0 selection 可能抵消了减少整层重算的收益。需要把计时拆成：layer-0 selection、完整层重算、稀疏 token 重算、cache merge、first-token finalization。
2. `ratio=0.10` 已经在多个高质量配置中表现不错，后续可以加密搜索 `0.05, 0.075, 0.125, 0.15`，看是否存在更低 token 重算比例但 F1 不掉的点。
3. 层段方面，`8-21`、`12-19`、`2-25`、`6-25`、`6-31` 是下一阶段重点。可以围绕这些层段左右平移或缩短，例如 `10-21`、`8-19`、`10-19`、`6-23`、`8-25`。
4. 目前 HotpotQA 50 的样本量适合筛选，但最终结论需要扩大样本或重复运行，因为 latency 受 GPU 状态影响，F1 也可能受小样本波动影响。
